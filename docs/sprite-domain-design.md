# 以精灵为中心的领域模型 —— 资产管理总设计

> 本文档是资产管理的**主设计**。此前的
> [资产生命周期方案](./asset-lifecycle-design.md)（分级回收）与
> [视频生成方案](./video-generation-design.md)（take 抽卡）中的机制仍然成立，
> 但作用单位从「会话」改为本文的「动作」。
> [UI/UX 方案](./ui-ux-design.md) 的导航层随之调整（见 §7）。

---

## 1. 为什么从「会话」换成「精灵」

现状：每次打开页面自动新建一个匿名会话（`81a6680d`），做完即弃。
问题不只是认不出谁是谁——**它和真实的生产单位错位了**：

实际工作方式（以现有素材为证）：

- 一个角色（cook / kozy_girl）= 一组动作（`角色动作_九宫格.json` 里的
  idle、walk、walk_luggage…每个 cell 一个动作）
- 每个动作各自要走完整条链：首帧 → 提示词 → 视频抽卡 → 抽帧 → 精修 → 导出循环
- 动作之间强关联：**同一角色必须长得一致**（下一个动作的首帧往往取自
  上一个动作的某一帧）、**导出规格必须统一**（同尺寸、同锚点、同命名）

会话模型里这些关系全部体现不了：9 个动作是 9 个互不相识的匿名会话，
一致性靠人肉记忆，追溯无从谈起。

**新模型：精灵是管理单位，动作是工作单位。**

## 2. 领域模型

```
精灵 Sprite（角色）
 ├─ 档案：名称、标签、立绘/参考图、备注
 ├─ 工艺预设 ProcessPreset：全精灵统一的抠图参数、输出尺寸、锚点、命名规则
 └─ 动作 Action[]（walk / idle / attack / …）
      ├─ 首帧 FirstFrame：来源可追（上传 | 参考图裁切 | 其他动作的第N帧 | 九宫格cell）
      ├─ 提示词 + 生成参数（model / seed / resolution / duration …）
      ├─ 抽卡 Take[]：每次生成一个（远端任务ID、视频文件、状态、成本）── 花过钱的源料
      ├─ 帧集 Frames：对选中 take 抽帧的结果（raw / proc）── 中间品，可重建
      ├─ 工序记录 Recipe：抽帧→去相似→抠图→缩放→…每步参数追加 ── 配方，必须保留
      ├─ 历史 History：帧级快照，撤销用 ── 中间品
      └─ 交付物 Artifact[]：精灵图 / GIF / Godot 资源 ── 最终价值
```

关键关系（这是会话模型给不了的）：

- **跨动作血统**：`walk 的首帧 = idle 的第 7 帧` 是一条显式记录的边。
  整个精灵的动作构成一张 DAG，任何一帧的来历都能一路追到最初的参考图。
- **精灵级一致性**：工艺预设挂在精灵上，动作默认继承——同一角色的所有
  动作用同一套抠图参数、导出同一规格。单个动作可覆盖，但覆盖会被标出来。
- **生命周期分级照旧**（源料/配方/中间品/交付物），只是按动作结算：
  一个动作定稿后回收它的中间品，不影响同精灵的其他动作。

## 3. 目录布局

```
data/
  sprites/
    sp_cook/
      sprite.json              # 档案 + 工艺预设 + 动作索引
      reference/               # 立绘、参考图、九宫格原图
      actions/
        act_walk/
          action.json          # 名称、状态、首帧来源、当前 take、覆盖的预设
          recipe.json          # 工序记录（追溯核心）
          takes/               # t_ab12.mp4 + t_ab12.json …（多次抽卡并存）
          frames/raw/  proc/
          history/
          exports/             # {name}-{run_id}/ 不可变目录
        act_idle/
          …
  library/                     # 跨精灵的交付物索引（缩略图墙用）
    index.json
```

`sprite.json` 要点：

```json
{
  "id": "sp_cook", "name": "厨师", "tags": ["主线", "NPC"],
  "preset": {
    "matting": {"model": "isnet-anime", "alpha_threshold": 128, "erode": 1},
    "output": {"frame_size": [256, 256], "anchor": "bottom-center",
               "naming": "{sprite}_{action}_{i:03d}"}
  },
  "actions": [
    {"id": "act_walk", "name": "walk", "status": "final"},
    {"id": "act_idle", "name": "idle", "status": "active"}
  ]
}
```

`action.json` 里的首帧来源（追溯的起点）：

```json
{"first_frame": {"kind": "action_frame", "action": "act_idle", "frame_index": 7}}
{"first_frame": {"kind": "grid_cell",   "image": "reference/九宫格.png", "cell": "walk"}}
{"first_frame": {"kind": "upload",      "file": "reference/walk_ref.png"}}
```

## 4. 与现有代码的映射：改动比看起来小得多

**核心决定：`Session` 类不废弃，降格为「动作的工作态」。**

现在的 Session = 视频 + 帧管理器 + 历史 + 磁盘目录——这正好就是一个动作
工作时需要的全部东西。改动：

| 现在 | 之后 |
| ---- | ---- |
| 会话 ID 随机生成、自动创建 | **ID 即 action_id**，由「打开动作」创建 |
| 目录 `data/sessions/{hex}` | `data/sprites/{sid}/actions/{aid}` |
| 关不掉、认不出、做完即弃 | 持久实体，重启后按 action_id 恢复（复用刚做的 `_restore`） |

于是：

- **现有 `/api/sessions/{id}/...` 端点树原样保留**（前端几十处调用不用改），
  `{id}` 传 action_id；`POST /api/sessions` 匿名创建废弃
- FrameStore、JobManager、会话锁、重启恢复、历史快照——**全部照旧**
- 新增薄薄一层精灵管理 API（见 §6）

这是整个设计里最重要的工程判断：**换的是寻址方式和目录根，不是运行时机制。**

## 5. 追溯（可追溯 = 三张网）

**① 工序链（动作内）**——`recipe.json`，每个副作用操作追加一条：

```
首帧(idle#7) → 生成(seed42,720p,5s) → take t_ab12 → 抽帧(0-5s,12fps,61帧)
→ 去相似(contour,0.95,-43帧) → 抠图(isnet-anime,128,1) → 缩放(50%)
→ 导出 sprite_sheet(columns=6) → artifact a_7f3d
```

**② 血统边（动作间）**——首帧来源记录构成精灵内 DAG：

```
参考图 ─┬─► idle ──第7帧──► walk ──第3帧──► walk_luggage
        └─► attack
```

**③ 成本账（take 级）**——每个 take 记录 model/seed/参数/远端任务ID/花费，
抽了几次卡、哪次成了，一目了然。

对应三个追溯问题的答案：

- 「这张精灵图怎么做出来的？」→ 工序链，一键复现（replay）
- 「这个动作的角色形象从哪来的？」→ 血统边，一路回到参考图
- 「这个角色花了多少生成费用？」→ 成本账，按精灵汇总

## 6. API 增量

```
GET/POST      /api/sprites                       精灵列表 / 建精灵
GET/PATCH/DEL /api/sprites/{sid}                 档案与工艺预设
POST          /api/sprites/{sid}/actions         建动作（含首帧来源）
GET           /api/sprites/{sid}/actions         动作看板（状态、封面、进度）
POST          /api/sprites/{sid}/actions/{aid}/open      打开→返回工作态(≈现session)
GET           /api/sprites/{sid}/lineage         血统图（节点=动作，边=首帧来源）
GET           /api/sprites/{sid}/cost            生成成本汇总
POST          /api/sprites/{sid}/grid-import     九宫格导入：一张图/一个视频批量建动作
```

`grid-import` 直接对接你现有的 `角色动作_九宫格.json` 工作流：
上传九宫格 + cell 定义 → 一次建出 9 个动作，每个动作的首帧即对应 cell，
来源标记为 `grid_cell`。

工作台内的一切（抽帧/抠图/导出/历史/任务）继续走现有 `/api/sessions/{aid}/...`。

## 7. UI：三层结构

```
精灵库（首页）          精灵详情（动作看板）         动作工作台（现有四步流水线）
┌──────────────┐      ┌──────────────────┐      ┌────────────────────────┐
│ [厨师]  [女孩] │  ──► │ 厨师              │  ──► │ 厨师 / walk            │
│ [史莱姆] [+新建]│      │ ├ idle   ✓已导出  │      │ ①素材 ②抽帧 ③精修 ④导出 │
│              │      │ ├ walk   ●精修中  │      │ （即现有工作台+步骤条） │
│ 卡片=立绘+进度 │      │ ├ attack ▢未开始  │      │                        │
└──────────────┘      │ [九宫格导入][+动作] │      └────────────────────────┘
                      │ 工艺预设 · 血统图   │
                      └──────────────────┘
```

- **精灵库**取代「每次启动新建匿名会话」：启动即见所有角色与各自进度
- **动作看板**是精灵的作战地图：每个动作一张卡（封面 = 最新帧/take 首帧），
  状态徽标（未开始/生成中/精修中/已导出），点进即打开工作台
- **工作台**就是 UI/UX 方案里的四步流水线，顶部加面包屑
  `厨师 / walk`；「以第 N 帧为首帧新建动作」按钮把跨动作血统变成一次点击
- 批量入口在看板层：「用统一预设导出全部已完成动作」「九宫格导入」

UI/UX 方案 §2 的导航分组相应改为：顶层 = 精灵库/资产库/存储，
制作四步移入动作工作台内部。

## 8. 迁移与实施顺序

**迁移**：现有 `data/sessions/*` 不动。新建「未归档」虚拟精灵，旧会话作为
其孤儿动作可浏览；提供「移入精灵」操作逐个认领。不做自动转换。

**顺序**（每步独立可交付）：

1. **实体层**：sprite.json / action.json 读写 + 精灵 CRUD API
   （不动现有工作台，先让精灵和动作存在）
2. **寻址切换**：打开动作 → 以 action_id 建工作态；目录根迁到
   `sprites/{sid}/actions/{aid}`；匿名会话创建下线
3. **前端三层**：精灵库页 + 动作看板页 + 工作台加面包屑
4. **recipe 记录 + 首帧来源**（追溯数据开始积累；「以帧为首帧建动作」）
5. **工艺预设**：精灵级默认参数下发到工作台表单
6. **九宫格导入**
7. 血统图 / 成本汇总 / 生命周期回收（沿用已有方案，单位换成动作）

视频生成方案的 take 模型原样挂到 action 下（§3 目录已含），两条线不冲突：
take 是动作的源料，生成表单在工作台「①素材」步。
