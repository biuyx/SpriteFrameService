# 资产生命周期管理 —— 设计方案

配套文档：[视频生成接入方案](./video-generation-design.md)

---

## 1. 现状诊断（实测，非推测）

对 `data/` 下 7 个会话取样（总 756 MB）。取其中数据最完整的一个会话：

| 部分 | 体积 | 性质 |
| ---- | ---- | ---- |
| `video/` | 2.7 MB | **源料** |
| `frames/raw/` | 57.1 MB | 中间品 |
| `frames/proc/` | 64.0 MB | 中间品 |
| `history/` | 57.7 MB | 中间品 |
| `exports/` | 86.6 MB | 交付物 + 重复 |
| `preview/` | 3.9 MB | 中间品 |
| **合计** | **273 MB** | |

暴露出四个问题：

**① 同一批像素存了四份。** raw、proc、history 快照、导出的单帧 PNG，都是同一角色
的同一批帧。约 220 MB 是近似重复的像素数据，而真正的交付物（精灵图 + 布局 JSON）
只有 43 MB，其中 JSON 仅 14 KB。

**② 结果无法复现。** 导出的 `sprite.json` 只有布局坐标（x/y/w/h），
`frames.json` 只有帧自身的路径与状态。**没有任何地方记录**：源视频是什么、
抽帧的起止与 fps、用了哪个抠图模型与什么参数、缩放裁剪怎么设的。
一个效果好的结果，下次做不出来；一个效果差的结果，追不到原因。

**③ 同名导出会混批。** `SessionStorage.export_dir()` 只做 `mkdir(exist_ok=True)`，
从不清理。上面那 86.6 MB 就是精灵图、GIF、122 张单帧三次导出堆在同一目录的结果。
这不只是占空间——先导出 122 帧的表，再用同名导出 10 帧的表，
旧的 `sprite_0010..0121.png` 会留着，而 `sprite.json` 描述的是新布局，
`/export/list` 把它们一并列出。**这是正确性缺陷。**

**④ 空会话不回收。** 7 个会话里 3 个是空壳——点了「新建项目」就留下目录，无人清理。

叠加背景：D 盘已用 95%（剩 21 GB）；而视频生成上线后，每次抽卡都会新增一个视频 take。

## 2. 核心思路：按「可再生性」给资产分级

生命周期管理的支点不是「用了多久」，而是**「丢了能不能再造出来，代价多大」**。

| 级别 | 内容 | 可再生性 | 策略 |
| ---- | ---- | ---- | ---- |
| **源料 source** | 上传/生成的视频、首帧图 | 上传的丢了要重传；**生成的丢了要重新花钱** | 必须保留 |
| **配方 recipe** | 抽帧参数、抠图模型与参数、缩放/裁剪、循环设置、生成 prompt/seed/model | 不可再生（但极小，几 KB） | **必须保留，优先级最高** |
| **中间品 derived** | raw / proc 帧、history 快照、preview | **有源料 + 配方就能完整重建** | 可随时回收 |
| **交付物 artifact** | 精灵图、GIF、WebP、Godot 资源、布局 JSON | 可由源料+配方重建，但它是最终价值 | 长期保留 |

结论直接落地为一句话策略：

> **保住源料、配方、交付物；中间品随时可丢、按需重建。**

按实测数据，这条策略能把一个「已定稿」会话从 273 MB 压到约 **46 MB**（源料 2.7 +
交付物 43 + 配方几 KB），**降幅 83%**，且不损失任何不可再生的东西。

## 3. 生命周期状态机

```
  新建 ──► draft ──► active ──► final ──► archived
            │          │          │           │
         空壳超时    正常工作   已产出交付物   仅留交付物+配方
         直接删除    全量保留   回收中间品     源料可外移
```

| 状态 | 触发 | 保留 | 回收 |
| ---- | ---- | ---- | ---- |
| `draft` | 新建会话 | 全部 | 无视频且 N 天未访问 → **整个删除** |
| `active` | 上传/生成了视频 | 全部 | 无（工作中） |
| `final` | 用户点「定稿」，或产出交付物后 N 天未访问 | 源料 + 配方 + 交付物 | 中间品（raw/proc/history/preview） |
| `archived` | 用户手动归档 | 配方 + 交付物 | 源料（可选打包到冷存目录） |

状态写进会话根的 `session.json`（新增），连同名称、标签、最后访问时间。

**顺带解决**：会话现在只有 12 位十六进制 ID（`d0491359`），界面上完全认不出谁是谁。
`session.json` 里加 `name` / `tags`，会话列表按名称展示。

## 4. 配方（recipe）：让中间品可丢、让结果可复现

在会话根维护 `recipe.json`，**每次产生副作用的操作都追加一条**：

```json
{
  "source": {
    "kind": "generate",
    "take_id": "t_ab12",
    "model": "doubao-seedance-1-0-pro-250528",
    "prompt": "角色向前走，循环动作",
    "params": {"resolution": "720p", "ratio": "1:1", "duration": 5, "seed": 42},
    "remote_task_id": "cgt-xxx"
  },
  "steps": [
    {"op": "extract",    "start_time": 0, "end_time": 10, "fps": 12},
    {"op": "remove_similar", "mode": "contour", "threshold": 0.95, "removed": 43},
    {"op": "background", "mode": "ai", "model": "isnet-anime",
     "params": {"alpha_threshold": 128, "erode": 1, "feather": 0}},
    {"op": "scale",      "mode": "percent", "percent": 50},
    {"op": "export",     "format": "sprite_sheet", "columns": 3,
     "artifact": "a_7f3d", "frame_ids": ["...", "..."]}
  ]
}
```

带来三件事：

1. **中间品可丢**：删掉 raw/proc 后，按 recipe 从源视频重跑即可还原（除 AI 抠图有
   微小随机性外，参数完全确定）
2. **结果可复现**：`POST /recipe/replay` 一键重跑整条链
3. **可追因**：某次导出边缘发白，直接看它当时的 `background` 参数——
   比如是不是踩了 `alpha_threshold=10` 那个坑

生成环节的 `seed` + `prompt` + `model` 让**连视频本身都可复现**（同 seed 同参数）。

## 5. 资产库：把交付物从会话里捞出来

现在交付物埋在 `data/sessions/{hex}/exports/` 下，会话一删就没了，跨会话也没法检索。

新增与会话解耦的库：

```
data/library/
    index.json                  # 全部交付物的索引
    a_7f3d/
        sprite.png
        sprite.json
        cover.jpg               # 缩略图
        recipe.json             # 该交付物的完整血统快照
```

- 导出成功后自动登记（或用户点「收入资产库」）
- 每个交付物带 `name` / `tags` / `created_at` / `source_session`
- 会话被删除或归档，**交付物仍在**
- 新增「资产库」页：缩略图墙、按标签筛选、查看血统、一键复现

同时修掉 §1③ 的混批缺陷：**每次导出用独立的不可变目录**
（`exports/{name}-{run_id}/`），旧批次不再被覆盖或混淆。

## 6. 空间治理

```ini
SPRITE_DISK_BUDGET_GB=50           # data/ 的软上限，超出触发回收
SPRITE_DRAFT_TTL_DAYS=3            # 空草稿会话保留天数
SPRITE_FINAL_RECLAIM_DAYS=14       # final 会话多久后回收中间品
SPRITE_MAX_TAKES_PER_SESSION=10    # 每会话最多保留的视频版本数
```

回收顺序（先便宜后昂贵，永不触碰源料/配方/交付物）：

```
preview → history 快照 → proc 帧 → raw 帧 → 超量的旧 take
```

- 一个轻量后台任务定期执行（复用现有 `cleanup_idle` 的调度位置，它现在**定义了却
  没有任何定时器调用**）
- 「存储」页展示：总占用、各会话占用与状态、可回收空间、一键回收按钮
- 回收是**幂等且可解释**的：告诉用户回收了什么、能否重建、怎么重建

## 7. 与视频生成的衔接

视频生成让生命周期管理从「优化项」变成「必需项」：

- **take 是源料，且是花过钱的源料** —— 回收策略必须永不自动删除生成的 take，
  只能由用户显式删除，且删除前提示「该视频由生成产生，删除后需重新付费生成」
- **抽卡会放大存储压力** —— `SPRITE_MAX_TAKES_PER_SESSION` 与「只保留已选中 +
  最近 N 个」的策略是必要的
- **recipe 让抽卡有意义** —— 记下每次的 prompt/seed/参数，好的那次才能复现和微调；
  否则抽到好结果也只是运气
- **失败的生成任务要有归宿** —— status=failed 的 take 只留 meta（含错误原因），
  不占空间，但保留记录以免重复踩同样的参数

## 8. 顺带修掉的既有缺陷

| 缺陷 | 现状 | 处理 |
| ---- | ---- | ---- |
| 同名导出混批 | `export_dir` 从不清理，多批次文件混在一起，`sprite.json` 与实际文件不一致 | 改为不可变的 `{name}-{run_id}/` 目录 |
| 空会话不回收 | 7 个会话中 3 个空壳 | draft 状态 + TTL |
| `cleanup_idle` 是死代码 | 定义了但无任何定时器调用 | 挂到后台回收任务上 |
| 精灵图无尺寸校验 | 实测导出过 10008×12232 的图，超出多数引擎 8192 的纹理上限 | 导出前按目标平台上限告警并建议分页 |
| 单帧与精灵图重复导出 | 一次精灵图导出附带 122 张单帧，重复 44 MB | 默认关闭单帧输出，需要时显式勾选 |

## 9. 改动清单

**新增**

- `services/asset_store.py` —— `session.json` / `recipe.json` 读写、状态迁移
- `services/library.py` —— 资产库索引与登记
- `services/reclaimer.py` —— 分级回收器 + 磁盘预算
- `api/library.py`、`api/storage_api.py` —— 资产库与存储治理端点
- `frontend/src/views/LibraryView.vue`、`StorageView.vue`

**修改**

- `services/storage.py` —— 导出目录不可变化；take 化（与视频生成方案共用）
- `services/session.py` —— 会话带名称/状态/标签；`_restore()` 读 `session.json`
- 各 `api/*.py` —— 每个副作用操作追加一条 recipe step（约每处 2 行）
- `main.py` —— 挂上定期回收任务

**顺序建议**

1. `session.json`（名称 + 状态）—— 无依赖，先让会话认得出
2. 导出目录不可变化 —— 修正确性缺陷，独立可测
3. `recipe.json` 记录 —— 每个 API 加两行，先只记不用
4. 分级回收器 + 存储页 —— 见效最大（实测可省 83%）
5. 资产库 —— 依赖 recipe，最后做

第 1–4 步与视频生成完全无关，可以并行推进；第 5 步和视频生成的 take 模型有交叉，
建议在 take 存储模型落地后再做。

## 10. 待决策

| 项 | 说明 |
| ---- | ---- |
| **自动回收的激进程度** | 建议默认「只提示不自动删」，用户在存储页确认后执行；纯自动回收对创作类工具风险偏高。 |
| **资产库是否跨会话去重** | 同一角色多次导出会产生近似文件。可按内容哈希去重，但会增加复杂度，建议先不做。 |
| **归档后的源料去向** | 打包成 zip 留在本机，还是移到外部目录/网盘？内网多人使用时，是否需要共享库？ |
| **多人场景的归属** | 服务已可对内网开放。资产库是全局共享，还是按访问令牌区分归属？当前认证是单一共享令牌，没有用户概念——若要区分，需要先引入用户维度。 |
